## Учебный этап — остальные модели

4 октября пользователь запросил код оставшихся файлов model для самостоятельного ввода. Подготовить четыре отдельных Java-файла с package com.example.smarthome.model. Код в чат не считать автоматически внесённым в проект.

Согласованные в инструкции имена:

### Что в HTML недоделано и не должно вводить в заблуждение

- «Сохранить» не сохраняет значения; повторное открытие возвращает исходные данные. В Android нужен согласованный источник состояния карточек и диалогов.
- Выключатель ленты, регулятор температуры света и выключатель клапана не имеют логики. Они входят в план, потому что явно представлены как органы управления.
- Переключение реле в модальном окне не обновляет карточку; состояние контакта остаётся статичным.
- Подключение всегда завершается успехом примерно по таймеру и не добавляет новую карточку. После закрытия и повторного открытия форма не сбрасывается. Для Android нужны повторный вход, проверка результата и предотвращение дублирующего запуска.
- Не определено, как новое ESP32 сообщает тип, имя устройства и комнату. Не придумывать дополнительные поля/мастера в интерфейсе до согласования этого пробела.
- Надпись об обновлении в реальном времени не подтверждена сетевой логикой. Механизм и период обновления показаний отсутствуют.
- CSS содержит оформление `.empty`, но соответствующего блока в HTML нет. Не считать его отдельным готовым экраном; после выбора пустой комнаты достаточно корректного пустого списка и нулевого счётчика.
- В HTML для «⋮» нет обработчика, но пользователь уточнил его назначение: переименование устройства на карточке. Это обязательная функция приложения. Значок уведомлений и аватар по-прежнему без согласованного действия; дополнительные экраны для них не придумывать.

Поток: экран → DeviceControlService → ControllerGateway → результат/измерение → HomeRepository → обновление экрана. Создание комнаты и фильтрация остаются локальными действиями приложения. Реальный транспорт не должен напрямую изменять TextView или Switch.

До реализации согласовать операции и данные:
- Изменить ленту: идентификатор устройства, питание, яркость и относительная температура света 0–100.
- Изменить реле: идентификатор и требуемое питание.
- Изменить клапан: идентификатор и требуемое положение; соответствие переключателя открытому клапану согласовать.
- Запросить/получить состояние устройства: доступность и подтверждённые параметры; для воды — уровень, температура и время измерения. Неизвестное значение не заменять нулём.
- Запустить подключение: SSID и пароль; получить этап, прогресс (если известен), результат и сведения об устройстве. Как присвоить имя и комнату, ещё не решено.
- Получать дальнейшие обновления показаний и потери связи без действий пользователя.

Команды асинхронные: результат приходит через обычный Java callback с успехом или ошибкой, а не немедленный boolean. В ответе нужны идентификаторы устройства и запроса, чтобы не спутать одновременные команды. Требуемое значение и подтверждённое состояние различать; при ожидании показывать процесс, при отказе сохранять последнее подтверждённое состояние. Обновление Android Views выполнять в главном потоке. Подписки освобождать при завершении экрана; поздние ответы не должны обращаться к уничтоженной Activity. Пароль не хранить в журнале и контексте.

Проценты прогресса не выдумывать, если настоящий транспорт сообщает только этап. В демонстрационном режиме можно имитировать успех и ошибку, явно обозначая этот режим. Нельзя обозначать демо как подключение к настоящему ESP32.

План передачи третьему участнику: работающее демоприложение, модели данных, ControllerGateway с согласованными методами, демонстрационная реализация и будущий `Docs/CONTROLLER_INTEGRATION.md` с единицами измерения, результатами, ошибками и местом замены демореализации. Этот отдельный документ и Java-файлы пока не созданы. Критерий подготовки: замена DemoControllerGateway на реальную реализацию не требует переписывать карточки и диалоги.

## Удаление комнат и устройств — уточнение пользователя

Пользователь предложил добавить удаление комнаты вместе с привязанными устройствами. Включено в план; реализация ещё не выполнена. Дополнительно предложено отдельное удаление устройства из меню его карточки.

- Отдельное меню комнаты: «Переименовать», «Удалить комнату вместе с устройствами». В исходном макете у комнат меню нет; его размещение согласовать. Меню устройства не должно неожиданно удалять всю комнату.

Наша логика в HomeRepository:
- `removeDevice(int deviceId)` удаляет запись одного устройства, сохраняя комнату.
- `removeRoomWithDevices(int roomId)` сначала проверяет существование комнаты, затем удаляет устройства с таким roomId и саму комнату как одну логическую операцию. Устройства других комнат сохраняются. Названия могут повторяться, поэтому удалять только по id.

- Проверки: пустая комната; несколько устройств; нетронутые соседние комнаты; неизвестный id; отдельное устройство; неизменность состояния при отмене (репозиторий не вызывается).
- После удаления не использовать прежний id повторно; поздние ответы контроллера не должны восстанавливать удалённую запись. Удаление данных приложения само по себе не сбрасывает ESP32, не стирает его Wi-Fi и не выключает физическое устройство.

Удаление относится к спискам в HomeRepository. Не добавлять delete в Room/Device: отдельная модель не владеет списками других объектов. Для диалогов подтверждения достаточно стандартных Android-диалогов; отдельные классы и XML пока не обязательны. Для меню комнаты запланирован `res/menu/menu_room_actions.xml`; в `res/menu/menu_device_actions.xml` добавить пункт удаления устройства. Это задачи первого участника.

## Начальное состояние при подключении

Пользователь уточнил: приложение должно получать реальное начальное состояние подключаемого устройства, а не показывать его выключенным по умолчанию. Различать online (доступность контроллера) и poweredOn (включена ли лента/нагрузка реле). Присваивание полю модели не отправляет команду выключения оборудованию.

Актуальная инструкция меняет конструкторы:
- Device(int id, String name, int roomId, String controllerId, boolean online) сохраняет переданное online вместо постоянного false.
- LightDevice(int id, String name, int roomId, String controllerId, boolean online, boolean poweredOn, int brightness, int lightTemperature).
- RelayDevice(int id, String name, int roomId, String controllerId, boolean online, boolean poweredOn).
- WaterDevice(int id, String name, int roomId, String controllerId, boolean online). Уровень, температура, время, статус и клапан остаются неизвестными до показаний; заполняются из ответа через updateReadings/setValveOpen.

Все наследники передают online в super. poweredOn уже был параметром предложенных конструкторов LightDevice/RelayDevice и сохраняется отдельно. При подключении интеграция получает начальное состояние, затем создаёт соответствующую модель и передаёт её приложению. Пока питание неизвестно, показывать ожидание/«Состояние неизвестно», не подставлять false; для текущих конструкторов ленты/реле создавать полностью инициализированную модель после получения нужных данных. При потере связи сохранять последнее известное питание, меняя доступность; не выдавать устаревшее значение за новое измерение.

Проверки для будущей реализации: online=true/poweredOn=true; online=true/poweredOn=false; потеря связи не выключает модель питания; отсутствие ответа не отображается как выключенное устройство. Отображение и реальный источник данных делают соответствующие участники. Мы определяем поля и методы.

При последней проверке Device заполнен пользователем, но конструктор ещё принимает четыре аргумента и задаёт online=false. LightDevice/RelayDevice/WaterDevice пока пустые. Новые сигнатуры выданы для самостоятельного ввода, исходники не изменены, сборка не запускалась.
