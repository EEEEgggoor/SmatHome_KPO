# Подключение интерфейса к данным и управлению

Исходный план на 18 октября 2026 года. Ветка `SmartHome_App`, Android-проект находится в одноимённой подпапке репозитория. Документ для участника, который пишет интерфейс.

На 20 октября 2026 года `MainActivity` использует Room через `HomeRepository`, а кнопка добавления открывает диалог USB/Wi-Fi подключения через `Esp32ControllerGateway`. В Android реализованы TCP-команды `0x01` (состояние), `0x02` (вода), `0x03` (питание/яркость света), `0x04` (реле). Проверенная прошивка ESP `9d04286` пока поддерживает только `0x01`, обработчики новых команд добавляет автор ESP. Gateway готов принимать вызовы сервиса; управление клапаном пока не поддерживается. Формат пакетов описан в CONTROLLER_INTEGRATION.md.

## Что уже готово

- `model/`: комнаты, свет, реле, вода; переименование, проверка значений, отдельные признаки `online` и `poweredOn`.
- `data/database/`: Room, таблицы, DAO, постоянное хранение и каскадное удаление устройств комнаты.
- [HomeRepository](../app/src/main/java/com/example/smarthome/data/HomeRepository.java): асинхронное чтение и изменение данных; callback приходит в главный поток.
- [DeviceControlService](../app/src/main/java/com/example/smarthome/service/DeviceControlService.java): команды, чтение состояния, подписки, подключение нового устройства, проверка ответа и сохранение подтверждённого состояния.
- [DeviceValueFormatter](../app/src/main/java/com/example/smarthome/presentation/DeviceValueFormatter.java): готовые строки для отображения.

Реальная реализация `ControllerGateway` добавлена для USB CDC, TCP-чтения и отправки команд света/реле с проверкой подтверждений. Демоконтроллер в приложении не используется. Fake находится только внутри тестов.

## Что требуется заменить в UI

На момент подготовки исходного плана `MainActivity` создавала списки через `DemoHomeData`, а кнопка подключения была заглушкой. Сейчас списки и изменения подключены к `HomeRepository`, а диалог добавления вызывает `DeviceControlService`. Обработчики управления пока показывают ограничение прошивки: ESP не исполняет эти команды.

1. Создать общие для приложения `SmartHomeDatabase`, `HomeRepository`, реальный gateway и `DeviceControlService`. Использовать application context для базы; не создавать сервис при каждом открытии диалога. Конкретный gateway передаёт участник контроллеров.
2. Заменить `DemoHomeData` загрузкой из репозитория. Восстанавливать выбранную комнату и корректно показывать пустые списки, ожидание и ошибки.
3. Перевести изменения комнат и имён устройств на методы репозитория. Обновлять список после успешного callback; идентификаторы брать из возвращённых моделей, а не из `createNextRoomId()`.
4. Переделать диалоги управления на асинхронное ожидание результата сервиса.
5. Подключить обновления состояния и освобождение подписок при уходе с экрана.
6. Реализовать экран подключения совместно с участником контроллеров и проверить всё на оборудовании.

## Методы для экранов

| Действие | Метод |
| --- | --- |
| Получить комнаты | `repository.getRooms(callback)` |
| Все устройства | `repository.getDevices(callback)` |
| Устройства комнаты | `repository.getDeviceByRoom(roomId, callback)` — именно такое имя сейчас в коде |
| Добавить / переименовать комнату | `addRoom(name, callback)` / `renameRoom(id, name, callback)` |
| Удалить комнату и её устройства | `deleteRoom(id, callback)`; сначала показать подтверждение |
| Переименовать / удалить устройство | `renameDevice(id, name, callback)` / `deleteDevice(id, callback)` |
| Управлять реле | `service.setRelayState(relay, poweredOn, callback)` |
| Управлять светом | `service.setLightState(light, poweredOn, brightness, lightTemperature, callback)` |
| Открыть / закрыть клапан | `service.setValveOpen(water, valveOpen, callback)` |
| Запросить состояние | `service.readDeviceState(device, callback)` |
| Наблюдать изменения | `service.subscribeToDevice(device, callback)` |

Все методы сервиса и `cancel()` вызываются из главного потока. Вкладка «Все» использует `getDevices`, а не выдуманный `roomId = 0`. Удаление записи устройства не отключает и не сбрасывает физический контроллер.

## Асинхронные диалоги

Сейчас `LightControlDialog`, `RelayControlDialog` и `WaterControlDialog` находятся в `ui/dialog/`. Их обработчики `onLightApplyRequested`, `onRelayApplyRequested`, `onValveRequested` возвращают `String` синхронно. Этот механизм нужно изменить: нельзя запустить команду и сразу вернуть успешный результат.

При отправке блокировать повторное применение для этого устройства и показывать ожидание. Сервис разрешает независимые устройства, но отклоняет параллельную операцию того же `device.id`. Callback имеет три исхода:

- `onSuccess(savedDevice)`: оборудование подтвердило команду, запись сохранена; заменить модель в списке по `id`, обновить карточку и завершить ожидание.
- `onError(error)`: снять ожидание, показать ошибку, сохранить последнее известное состояние. Тайм-аут не доказывает, что оборудование не выполнило команду; не отправлять её автоматически повторно.
- `onStateSaveError(confirmedDevice, error)`: оборудование подтвердило состояние, но сохранить его не удалось. Отобразить подтверждённое состояние с сообщением об ошибке хранения; повторно согласовать данные с устройством и базой. Не показывать обычный успешный результат и не повторять команду вслепую.

Сервис не изменяет модель, которую получил от UI. Не устанавливать `poweredOn` или положение клапана заранее. Выключенный свет может сохранять яркость и температуру света. `online = false` не означает выключенное питание.

Обработчики команд должны учитывать жизненный цикл Activity/диалога, например через ViewModel. Не обновлять уничтоженный экран. Для подписок хранить возвращённый `Subscription`, вызывать `cancel()` при прекращении наблюдения и заново загружать данные при возвращении. Один callback подписки получает много результатов. Отмена прекращает доставку событий, но не откатывает уже начатую запись в БД. Удаление устройства во время команды может закончиться подтверждением оборудования и ошибкой сохранения — учесть это в UI.

## Подключение нового устройства

Вызов: `service.connectDevice(name, roomId, ssid, password, connectionCallback)`. Комната должна существовать. SSID и пароль передавать без `trim()`; пустой пароль допустим. Не записывать пароль в логи или БД. Выбор физического устройства согласовать с участником контроллеров: текущая сигнатура не принимает аппаратный адрес.

Метод возвращает `ConnectionAttempt`. Процесс асинхронный: `onProgress(stage, nullablePercent)`, затем `onSuccess(savedDevice)` или `onError(error)`. Этапы из `ControllerGateway.ConnectionStage` переводить через `strings.xml`; `null` процента означает неопределённый прогресс. Отдельный `onStateSaveError(ConnectionInfo, error)` означает, что устройство подключилось, но запись не создана. `ConnectionInfo` содержит сведения оборудования, а не готовый локальный `id`.

При закрытии экрана можно вызвать `cancel()`. Это подавляет дальнейшие callbacks, но уже переданные Wi-Fi-настройки и начавшееся сохранение не отменяются. После повторного открытия перечитать базу. Одновременно допускается одна попытка подключения. Ожидание команды — 10 секунд; всего подключения — 120 секунд до начала сохранения.

## Отображение значений

Создать `DeviceValueFormatter(getResources())`. Использовать методы `formatWaterLevel`, `formatTemperature`, `formatLastUpdate`, `formatLevelStatus`, `formatValveState`, `formatOnlineState`, `formatPowerState`, `formatBrightness`, `formatLightTemperature` вместо дублирования условий в Activity и адаптерах.

У воды `null` означает «ещё нет данных», а не ноль или закрытый клапан. `lastUpdate` — время измерения в миллисекундах Unix. Для актуальности текста «только что» периодически перерисовывать строку времени, не менять само время измерения. Задержанные или повторные показания воды сервис не записывает поверх более новых. Технический `levelStatus` и пользовательские сообщения согласовать с контроллером; строки интерфейса хранить в ресурсах.

## Приёмка интеграции

Проверить сохранность комнат и устройств после перезапуска, переименование, каскадное удаление, команды с подтверждением/ошибкой/тайм-аутом, offline при сохранённых показаниях, отмену подключения и поворот экрана во время операции. Не писать телеметрию в репозиторий параллельно сервису: его порядок операций рассчитан на один общий экземпляр.

Тесты сервиса используют реальную Room в памяти и управляемый fake. Они проверяют логику сервиса, но не подключение текущего UI и не физическое оборудование. Задачи участника контроллеров описаны в [CONTROLLER_INTEGRATION.md](CONTROLLER_INTEGRATION.md).


## Уточнение после добавления команд, 20 октября 2026

- Запрет добавления LIGHT без температуры снят. Температуры света/воды не входят
  в текущую задачу оборудования: убрать их элементы из диалогов. В setLightState
  передавать прежнее device.getLightTemperature() для совместимости модели, а не
  показывать это поле как действительную настройку. Новая модель начинает с 0.
- Из обработчиков MainActivity вызывать setRelayState/setLightState сервиса;
  блокировать повторное нажатие на время запроса. Успех/ошибка приходят асинхронно,
  возвращение null из старого синхронного обработчика само по себе не означает успех.
- У воды обновляется уровень; temperature/levelStatus/lastUpdate могут быть null.
  Не заменять неизвестное время текущим временем телефона и не показывать 0 °C.
- Изменение состояния карты подтверждать через callback сервиса. При ошибке и
  тайм-ауте нельзя показывать запрошенное значение как подтверждённое устройством.
