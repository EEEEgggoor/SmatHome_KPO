# Подключение реальных контроллеров

Состояние на 18 октября 2026 года. Ветка `SmartHome_App`; приложение — Java/Android, прошивку можно писать на C. Документ для участника, который реализует связь с оборудованием.

## Разделение ответственности

В приложении уже есть модели, Room, `HomeRepository` и [DeviceControlService](../app/src/main/java/com/example/smarthome/service/DeviceControlService.java). Сервис проверяет ответы, управляет ожиданием и сохраняет подтверждённое состояние. Он не реализует USB, Wi-Fi, HTTP, MQTT или прошивку.

Нужно реализовать Java-класс, например `Esp32ControllerGateway`, который выполняет [ControllerGateway](../app/src/main/java/com/example/smarthome/integration/ControllerGateway.java), и соответствующий протокол в прошивке. Java-интерфейс — действующий контракт приложения; это не реализация транспорта. Демоконтроллер в приложение не добавляем. Конкретный транспорт, обнаружение, разрешения Android и привязку к оборудованию определяет участник контроллеров совместно с автором UI.

## Сначала согласовать адресацию

`Device.id` и `roomId` — локальные идентификаторы базы, не номера GPIO и не адреса каналов. `controllerId` обозначает контроллер. В текущей модели нет отдельного `channelId`, а результат первого подключения ещё не содержит локального `device.id`: база создаёт его после ответа gateway.

До работы с несколькими каналами одного контроллера согласовать устойчивое соответствие «запись приложения → аппаратное устройство/канал». При необходимости добавить идентификатор канала, изменить контракт и миграцию базы совместно. Не вычислять аппаратный канал из случайного локального `id`. Метод `connectDevice` предполагает, что физическая цель уже выбрана или однозначно определяется реализацией; API выбора цели пока нет.

## Методы gateway

| Метод | Что требуется от оборудования |
| --- | --- |
| `readDeviceState(requestId, device, callback)` | Получить действительное состояние существующего устройства |
| `setRelayState(requestId, relay, poweredOn, callback)` | Установить питание реле и вернуть подтверждённое состояние |
| `setLightState(requestId, light, poweredOn, brightness, lightTemperature, callback)` | Установить питание и обе настройки света |
| `setValveOpen(requestId, water, valveOpen, callback)` | Открыть (`true`) или закрыть (`false`) клапан |
| `subscribeToDevice(device, listener)` | Доставлять изменения состояния и доступности; вернуть `Subscription` |
| `connectDevice(requestId, ssid, password, callback)` | Настроить сеть, прочитать начальное состояние; вернуть `ConnectionAttempt` |

Не изменять входную модель и не обращаться к Room из gateway. Возвращать отдельную модель того же класса, с теми же `id`, `roomId`, `controllerId` и именем. Сервис сохраняет метаданные записи через репозиторий.

## Потоки, подтверждения и ошибки

- Сервис вызывает gateway из главного потока; сетевую работу и ожидание выполнять в рабочем потоке. Все callbacks и события возвращать в главный поток Android, например через `Handler(Looper.getMainLooper())`.
- `requestId` — непрозрачный номер запроса. Вернуть его без изменений в `onSuccess(requestId, device)` либо `onError(requestId, deviceId, exception)`. Для одиночного запроса доставить ровно один конечный результат.
- Успех команды означает подтверждение применённого состояния оборудования. Успешная постановка пакета в очередь или отправка байтов сама по себе недостаточна.
- Ответ команды должен иметь `online = true` и запрошенные значения. Яркость и температура света — целые числа 0–100; температура света здесь не градусы Цельсия. Согласовать преобразование аппаратной шкалы без скрытого расхождения с запросом.
- `poweredOn` и `online` независимы. Выключение света не обнуляет настройки автоматически. Ошибка запроса не равна событию потери связи.
- Сервис ждёт ответ команды 10 секунд, подключение — 120 секунд. Он игнорирует поздний/повторный ответ, но это не отменяет физическое действие. Не повторять команды автоматически после тайм-аута; предусмотреть идентификацию запросов и порядок их исполнения на стороне протокола.
- Ошибки должны быть понятными и не содержать паролей. `null` вместо исключения недопустим. Ошибку работы с БД обрабатывает сервис, gateway её не маскирует.

Чтение может вернуть `online = false`: сервис обновит доступность и сохранит прежние показания. Модели света и реле не поддерживают неизвестное питание; не выдавать выдуманное `false` за известное начальное состояние. При невозможности получить обязательные данные первоначальное подключение завершается ошибкой.

## Данные воды

| Поле | Требование |
| --- | --- |
| `waterLevel` | Целое число 0–100 |
| `temperature` | Конечное число; NaN и бесконечность запрещены, аппаратный диапазон пока не закреплён |
| `levelStatus` | Непустой статус; пробелы по краям удаляются |
| `lastUpdate` | Положительное время измерения в миллисекундах Unix |
| `valveOpen` | `true` — открыт, `false` — закрыт, `null` — неизвестно |

Первые четыре поля приходят полным пакетом либо все `null`; клапан может быть неизвестен независимо. В модели используются `updateReading(...)` и `getLastUpdate()` — именно такие имена. Отсутствие показаний не заменять нулями. Команда клапана сама по себе не создаёт новое измерение.

Сервис сохраняет водные показания только если их время новее сохранённого. При одинаковом/старом времени показания остаются прежними, известное положение клапана может обновиться. Для `null` показаний репозиторий сохраняет прежние значения. Согласовать источник и синхронизацию времени: uptime контроллера нельзя выдавать за Unix-время. Округление текста делает `DeviceValueFormatter`, данные не нужно округлять ради интерфейса.

## Подписки и порядок событий

`DeviceListener.onStateChanged(device)` передаёт отдельную подтверждённую модель; `onAvailabilityChanged(deviceId, online)` меняет только доступность; `onError(deviceId, error)` сообщает ошибку и сам по себе не отменяет наблюдение.

Сервис использует одну подписку gateway на устройство и несколько независимых подписчиков UI. Реализация `Subscription.cancel()` должна быть повторно безопасной, освобождать ресурсы и прекращать доставку, включая уже поставленные в очередь callbacks.

Сервис сериализует записи для устройства, объединяет ожидающие обновления и отбрасывает ожидающие события, пришедшие до подтверждения команды. Поэтому подписки предназначены для актуального состояния, а не журнала всех измерений. Доставлять события в порядке подтверждённых изменений. Отдельной ревизии состояния реле/света в контракте нет: старый пакет, доставленный после нового подтверждения, нельзя представлять как новое событие.

## Первоначальное подключение

SSID и пароль передаются точно, без `trim()`; пустой пароль допустим для открытой сети. Не сохранять пароль в базе приложения, логах и ошибках. Отправку и хранение настроек на оборудовании определить в протоколе.

Допускается одна активная попытка подключения. `onProgress` сообщает один из этапов `SEARCHING_DEVICE`, `SENDING_WIFI_SETTINGS`, `CONNECTING_TO_NETWORK`, `READING_STATE`. Процент относится к текущему этапу: 0–100 или `null`, если неизвестен.

Завершить попытку одним подходящим callback:

- `onRelayConnected(requestId, controllerId, poweredOn)`;
- `onLightConnected(requestId, controllerId, poweredOn, brightness, lightTemperature)`;
- `onWaterConnected(requestId, controllerId, waterLevel, temperature, levelStatus, lastUpdate, valveOpen)`;
- `onError(requestId, exception)`.

Успех означает доступное устройство и подтверждённое начальное состояние. Имя и комнату выбирает UI; сервис создаёт запись и назначает локальный id через базу. Если запись не удалась, сервис отдаёт UI отдельный `onStateSaveError(ConnectionInfo, error)`: физическое подключение уже могло состояться.

`ConnectionAttempt.cancel()` прекращает попытку и доставку событий, допускает повторный вызов. Уже отправленные Wi-Fi-настройки не откатываются. Не отправлять итоговый callback после отмены. Поздние ответы дополнительно отсекает сервис.

## Что проверить перед передачей

На реальном оборудовании проверить все три типа, чтение начального состояния, недоступность и восстановление связи, повтор/задержку ответа, отмену подключения, неверные Wi-Fi-настройки и адресацию нескольких устройств. Убедиться, что callbacks идут в главном потоке, а I/O его не блокирует. Согласовать поведение после перезапуска приложения и контроллера.

Тесты `DeviceControlServiceTest` проверяют сервис с fake и реальной Room в памяти. Они не подтверждают протокол и прошивку. Запуск из папки `SmartHome_App` при работающем эмуляторе:

```powershell
.\gradlew.bat :app:assembleDebug :app:testDebugUnitTest
.\gradlew.bat :app:connectedDebugAndroidTest "-Pandroid.testInstrumentationRunnerArguments.class=com.example.smarthome.service.DeviceControlServiceTest"
.\gradlew.bat :app:connectedDebugAndroidTest "-Pandroid.testInstrumentationRunnerArguments.class=com.example.smarthome.data.HomeRepositoryTest"
```

После запуска проверять количество тестов и ошибки в XML-отчёте `app/build/outputs/androidTest-results/connected/debug/`, а не только надпись `BUILD SUCCESSFUL`. Инструкции для автора интерфейса — [UI_INTEGRATION.md](UI_INTEGRATION.md).
